First gate on this document.** **All three lanes independently found the same defect**, the strongest signal in the run: the ADR stated that a digest mismatch "is never skipped", while `scripts/build-linux.sh` ships a documented path that skips the check entirely — setting `SNATCH_APPIMAGETOOL` substitutes a caller's own packer and reaches `chmod +x` with nothing compared, printing `(unverified, caller's choice)`. A maintainer applying the rule literally would delete that branch as a breach, or add a digest check that defeats its purpose; an auditor would record the packer as always verified. **Two lanes found the Decision sentence false as written.** "Every artifact the build downloads is pinned … and verified against a recorded SHA-256" does not hold for PyPI: CI installs `ruff`, `pytest` and `pyinstaller` at exact versions and `requirements.txt` by version, with no `--require-hashes`. Verified by opening the install steps. `docs/building.md` was already correct here — it reserves its "(SHA-256 pinned)" annotation for the binary rows — so the ADR was the outlier, and the header line calling SNAT-0035 "the one open exception" compounded it. The section is now § Known exceptions and names all three. **Two lanes found the Consequences line contradicting the mpv bullet**: "a two-step edit — version, then digest" against "`MPV_WIN_TAG`, `MPV_WIN_ASSET` and the asset's digest move together", so a bump routine built from the consequence names an asset that does not exist. **Three single-lane findings, all material.** The ADR called a dated release tag "the only immutable identifier that repository offers" while its own exception section says a tag is a pointer its owner can move — two answers to what counts as an acceptable pin, and a builder taking up SNAT-0035 could close it with an exact tag under one and only a SHA under the other. It claimed "nothing in this repository watches for a newer yt-dlp" when `scripts/update-ytdlp-pin.sh` re-resolves the pin and has a `--check` mode that exits non-zero when behind — so an implementer would write a second resolver rather than call the one that ships; confirmed nothing schedules it, which is the true half of the claim. And the policy was silent on downloads the running app makes: the in-app yt-dlp self-update verifies against the release's own `SHA2-256SUMS` manifest, a deliberate second model, and conforming it to the recorded-digest rule is not possible. **Two collisions from this loop's own fixes, caught at 4a step 4**: the title still said "everything the build fetches" after the Decision was narrowed, and the signatures alternative argued against partial coverage in a document that had just admitted three gaps — reworded to argue for gaps being *enumerable*, which is the real distinction. **Ledgered `out_of_scope`:** `digest_for()`'s header comment in `scripts/fetch-binaries.sh` still says the mpv asset name "is resolved from the API at fetch time", which SNAT-0064 removed. All three lanes raised it. Code-side, so not carried into this document. **Open questions resolved clean, not counted:** whether `zizmor` runs in any gate (it does not; the ADR only reports what it says when run, which is accurate), and whether the pip installs are hash-pinned (they are not, which is what made finding 2 real rather than a wording gap). |
